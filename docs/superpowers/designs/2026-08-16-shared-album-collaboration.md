# 共享相册协作权限与 NFC 预览设计

## 目标

修复受邀成员完成 NFC 激活后仍可能无法进入预览的问题，并为同一份共享相册增加可动态切换的只读/读写权限。只读成员看到完整相册；读写成员使用与拥有者相同的 Canvas 编辑能力并直接发布新版本。

## 权限模型

`gift_members.role` 支持 `owner`、`viewer`、`editor`。邀请时由拥有者指定 `viewer` 或 `editor`，之后只有拥有者能直接修改成员角色。预览要求成员仍存在、当前账号与成员邮箱匹配、激活记录匹配当前环境账号、礼品为 `bound` 且共享开关开启。

`viewer` 只能读取完整快照。`editor` 在相同读取能力之上可以创建上传会话并提交新版本。成员删除、权限修改、整册删除等管理动作不因 `editor` 身份自动授权；编辑者只能创建待拥有者处理的管理申请。

## NFC 与预览

NFC 入口验证 token 和账号、写入激活记录后，如果相册已发布，直接导航到 `/gifts/shared/<giftId>`。共享详情页不再依赖 `/gifts?open=` 加载列表后查找相册。未发布时停留在明确状态页；以后从“我的纪念品”列表进入。

共享相册 API 返回角色、版本、完整页面 JSON 和每个媒体对象的签名读取 URL。客户端按页面内稳定的媒体引用恢复图片，不再依赖跨页的隐式顺序消耗；旧快照缺少稳定引用时保留顺序回退。只读和读写角色共用同一个读取 DTO 与预览组件。

## 共享编辑与并发

编辑器载入当前共享版本并将远端媒体下载/缓存为可供现有 `BookCanvasEditor` 使用的 URI。新增图片在提交时上传至当前环境私有 R2；未变化的远端媒体通过稳定 ID/Object Key 复用，避免每次编辑重复上传全部照片。

提交请求携带 `baseVersion`。完成上传时，服务端重新检查成员仍为已激活的 `editor`（拥有者也允许提交），锁定礼品对应共享相册并比较当前版本。版本相同才原子替换快照并递增版本；不同时返回 `409 gift_album_version_conflict`，客户端丢弃不可继续提交的上传会话并提示重新加载最新版。这里不实现实时合并。

## 管理审批

新增管理申请记录，类型限于 `delete_album`、`remove_member`、`change_member_role`。只有已激活的 `editor` 可创建申请；只有拥有者可批准或拒绝。批准时再次校验目标仍存在、申请仍待处理以及发起者当前仍有资格。拥有者直接执行相同操作时不需要给自己创建申请。

整册删除只删除云端共享快照及其媒体，不删除拥有者或成员设备上的本地相册。R2 删除继续通过 cleanup job 做 best-effort 清理；数据库权限撤销和删除结果不依赖对象清理成功。

## 安全与边界

- 所有成员与编辑鉴权均使用服务器统一账号会话和规范化邮箱，不信任客户端传入的角色或用户 ID。
- 上传对象键由服务端生成；页面 JSON 只能引用本次会话已验证的新媒体或当前礼品已有媒体。
- 创建上传会话与完成发布都检查停测开关、礼品状态、成员激活和当前角色。
- 不新增第三方服务、支付、分析、自动同步或客户端秘密。
- staging/production 的数据库、R2、token、激活和编辑版本严格隔离。

## 验收重点

覆盖 NFC 激活后直接预览、两种角色完整渲染、邀请及权限切换、权限撤销后的悬挂提交拒绝、完整 Canvas 编辑、媒体复用、新版本原子提交、并发版本冲突，以及受控管理申请的批准/拒绝。
