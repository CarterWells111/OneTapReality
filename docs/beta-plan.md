## 共同工作规则

- GitHub Issue / Project
  是唯一任务事实源；每个任务只能有一位负责人、一个验收条件和一个目标环境。

- 订单和收件信息只由你与硬件同学在受限表格中处理；不得放入
  GitHub、微信群、仓库或截图。

- 所有代码变更必须经 PR；所有生产、TestFlight、云端和 DNS
  操作必须先有外部运维记录与回滚说明。

- 测试卡只对应 staging；付费用户 production 卡在第 1
  周演练通过后才可写入与发货。

# 第 1 周：环境、样卡与招募准备

**本周目标：**完成 Beta
的技术与交付前置条件。不能证明端到端路径安全可用，就不收款、不写生产卡、不发货。

### 全栈 / 发布负责人

**本周主责：**建立独立 staging 并完成团队端到端演练。

- 按 Alpha staging 手册建立或明确阻塞项：独立 Railway 服务/数据库、R2
  bucket、域名、独立 secrets 与邮件测试配置。

- 完成 iOS
  实体样卡全流程：碰卡、深链、邮箱登录、认领、发布、受邀查看、停用、对象删除与
  P0 停测开关。

- 冻结首批 Beta 的功能范围；只接受 P0/P1 修复进入候选构建。

### 辅助开发

**本周主责：**为 Beta 路径补齐回归覆盖与缺陷分流。

- 核对激活、登录、认领、发布、停用与错误文案的自动测试；修复已确认 P1。

- 建立复现模板：设备、系统、构建号、卡批次、脱敏截图、预期与实际结果。

### 硬件设计与生产

**本周主责：**锁定最简单测试件并验证写卡工艺。

- 确认卡材、包装、批次编码、生产周期和单套成本；制作 3 张内部样卡。

- 对每张样卡读取、碰卡和跨设备抽检；只记录批次 ID 与状态，不记录完整
  URL/token。

### UI / 宣传

**本周主责：**准备招募、引导和反馈材料。

- 完成中文一页使用说明、包装内反馈二维码、受邀规则与不适用场景说明。

- 筛出首批 5 位确认用户与 15
  位候补；准备外部收款、退款、发货和群入群话术。

# 第 2 周：首批 5 套付费 Beta

**本周目标：**用最小可控批次验证收款、写卡、发货、激活、客服和反馈闭环。

### 全栈 / 发布负责人

**本周主责：**只处理首批路径稳定性与 P0/P1。

- 在第 1 周验收通过后，批准 production 礼品卡写入和对应 TestFlight
  构建；不自动扩大测试名单。

- 每天看脱敏激活漏斗与错误报告；P0 立即关闭 GIFT_SHARING_ENABLED
  并暂停发货。

### 辅助开发

**本周主责：**快速复现和小范围修复。

- 为每个有效缺陷建立 Issue；只处理会阻断激活、登录、认领、发布或隐私的
  P0/P1。

- 每个修复都通过 PR、目标测试和完整门禁。

### 硬件设计与生产

**本周主责：**生产、测试并发出首批 5 张卡。

- 付款确认后写入 5 张 production 卡；逐张读写验证与 iPhone
  碰卡抽检后再封装。

- 记录脱敏订单号、卡批次 ID、发货状态和异常，不记录完整礼品链接。

### UI / 宣传

**本周主责：**让首批用户能独立完成首次体验。

- 逐位发送统一的安装、激活、隐私和反馈指引；建立一个安静、可追溯的微信群节奏。

- 在激活后第 1 天和第 3
  天收集结构化反馈，归纳为体验、硬件、功能、文案四类。

# 第 3 周：扩量交付余下 15 套

**本周目标：**在首批数据证明可控后，完成余下 15
套交付，并保持问题处理速度和用户体验一致。

### 全栈 / 发布负责人

**本周主责：**批准扩量、控制发布节奏和回滚。

- 依据第 2 周周会作出 go / no-go；扩量前确认 production
  监控、停测开关、管理员停用能力有效。

- 只在无 P0 的候选版本上扩大 TestFlight 受邀用户；每次变更保留回滚方案。

### 辅助开发

**本周主责：**稳定已验证流程，避免功能漂移。

- 修复首批发现的 P1；把重复人工支持转为更清晰的错误文案、引导或测试。

- 不在本周引入与激活主路径无关的新功能。

### 硬件设计与生产

**本周主责：**完成余下 15 套的一致性生产与发货。

- 按已验证工艺写卡、抽检、封装和发货；出现读写异常即隔离整批并复检。

- 更新单套成本、返工率、物流时效和包装问题，为下月是否扩量提供数据。

### UI / 宣传

**本周主责：**提升完成率并形成可用洞察。

- 继续按统一节奏提醒安装、激活和反馈；把常见问题补入使用说明 v2。

- 每三天输出一页反馈摘要：高频卡点、正向时刻、引导误解和建议优先级。

# 第 4 周：收敛、复盘与 Beta 下一阶段决策

**本周目标：**把 20 套 Beta
转化为可验证的产品、硬件和运营决策，而不是只收集零散评价。

### 全栈 / 发布负责人

**本周主责：**完成 Beta 技术复盘与下阶段决定。

- 汇总
  P0/P1、稳定性、停测演练、隐私与停用删除验证；划分必须修复、可以观察和明确不做。

- 基于数据决定下月：继续 20 人 Beta、扩大规模，或暂停扩量修复。

### 辅助开发

**本周主责：**把已验证缺陷转成可维护改进。

- 完成已承诺 P1 或写清延后理由；为重复缺陷补测试，避免回归。

- 清理无主 Issue，保留下一月唯一优先级排序。

### 硬件设计与生产

**本周主责：**形成硬件可行性结论。

- 输出成本、良率、返工、物流、包装和用户操作问题；给出下一批建议数量与最小改版。

- 保留可追溯批次记录，处理未激活、退件或异常卡。

### UI / 宣传

**本周主责：**形成用户洞察和下一批表达。

- 将反馈按价值、易用性、信任、送礼动机和包装体验归类；产出一页 Beta
  洞察。

- 更新招募与使用说明，不把 Beta 反馈包装成公开承诺。

## 周会统一验收证据

- 软件：构建号、CI 链接、设备/系统、脱敏错误证据、回归结果。

- 硬件：卡批次 ID、写卡/抽检数量、异常数量、库存和发货状态。

- 用户：付款/激活/反馈的脱敏数量，不收集或公开照片、完整邮箱、验证码、token
