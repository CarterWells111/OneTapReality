## 一、这个项目现在是什么

**一句话**：情侣旅行后的送礼向纪念册 App —— 选本地照片 → 生成可编辑的旅行册草稿 → 存本地 SQLite → 城市收藏地图打卡 → 纪念品商店 → NFC 实体卡片解锁云端共享相册。

**技术栈**：Expo SDK 54 + expo-router（typedRoutes / reactCompiler 全开）+ expo-sqlite（本地主库 `luyi.db`）+ expo-router API Routes（服务端）+ drizzle-orm/pg + R2/S3 预签名上传 + Resend 邮箱验证码 + react-native-nfc-manager。

**先说客观优点**，因为下面全是刀：

- **111 个测试文件**。有迁移测试、路由测试、契约版本测试、CI workflow 测试。这在黑客松里属于罕见的工程纪律，评委问"你们怎么保证质量"时这是硬牌。
- 画布编辑器（拖拽/缩放/旋转/图层/贴纸/相框/背景）是真做出来的，`editor-pages.ts` 的纯函数拆分很干净。
- PDF 导出踩过的坑（iOS 忽略 `@page size`、多空白页）在注释里有完整记录并已修，说明是真跑通过的。
- 中国地图城市坐标做了墨卡托投影校准（`types/city.ts:62-78`），不是贴图糊的。

**先说一个非技术问题**：这个项目有**四个名字**——仓库叫 `Tralbum`，package/scheme 叫 `onetapreality`，首页标题写 `OneTapReality｜一触如初`，`AGENTS.md` 里叫「旅忆」，导出文件后缀又是 `.tralbum`。三份答卷 + 现场演示 + PPT 如果名字不统一，评委记不住你，也会觉得团队没想清楚自己在做什么。**今天第一件事是定一个名字，全局替换。**

## 二、最伤的三个结构性问题

### 1. 「AI 旅行册」里一行 AI 都没有

`src/services/ai/demo-draft-generator.ts` 就是全部的"生成"能力：

```
封面 headline = 用户填的标题
封面 body     = "${日期} · 在${城市名}慢慢走过的这一天"
每张照片一页  = headline 固定 "把这一刻留住"
                body 固定 "我们选了 N 张照片，记录这段只属于我们的旅程。"
尾页          = "下一次，继续一起出发"
```

选 20 张照片，就是 20 页**一模一样**的文案。这是字符串拼接，不是生成。

**更狠的一点：架构把 AI 主动焊死了。**

- `docs/AI-CONSTRAINTS.md` 明令：不读图像像素、不识别人物地点、禁止 `fetch`、禁止环境变量。
- `src/services/ai/remote-contract.ts:26-33` 在**类型层面**规定：发给服务端的只能是 `title / city / travelDate / photoCount`。
- `findPrivacyViolations()` 还专门写了正则去拦截照片 URI、data:image、经纬度。

也就是说：**即便今天接上 GPT，模型也只能看到"杭州 / 2026-07-25 / 8 张"，它永远写不出关于照片内容的一个字。** 这不是没时间做，是设计原则主动放弃了这个能力。

B站方向一的评分里 **AI 应用创新性占 40%**。你目前这一项接近 0。

**唯一的好消息**：插座已经焊好了。`createRemoteDraftGenerator(transport, consent)`（`remote-contract.ts:150`）是标准的依赖注入，只要塞一个 transport 进去，`MemoriesProvider` 换一行就能切。下午 4 小时能救回来，方案见第五节。

### 2. 产品叫 One Tap，真实流程是 Six Taps

`src/features/gifts/gift-entry.tsx` 的实际链路：

```
碰一下 NFC 卡
 → 没装 App？→ 只显示一句"请在 App 中打开礼品"→ 死路，没有网页版
 → 装 App
 → 输邮箱
 → 等 Resend 发邮件
 → 输 6 位验证码
 → claim
 → 终于看到照片
```

评委现场碰一下你的卡，会卡在"等邮件"那一步，然后现场安静十秒。**slogan 和实现正面打架**，而且这是最容易被抓住的那种打架。

第二层伤害：web 分支只有一句"请在 App 中打开"（`gift-entry.tsx:17`）。意味着**你的礼品链接发给任何人都打不开**。小红书赛道要求"能在小红书生态被使用/传播"，B站赛道要求"服务社区"——传播路径为 0，这两项都拿不到分。

### 3. 前后端是两套互不相通的系统

| | 本地 | 云端 |
|---|---|---|
| 存储 | expo-sqlite `luyi.db` | Postgres + drizzle |
| 主流程用哪个 | **全部** | **零** |

`/api/memories`、`/api/memories/[id]`（GET/POST/PUT/DELETE）、`server/auth/device-auth.ts` 的 Bearer token 鉴权、`devices` 表、`server/memories/repository.ts` —— 我全项目 grep 了一遍，**App 里没有任何一处调用**。`BackendApiClient` 只被 `/backend` 调试页和 gift 流程用到。

结论：**你写的旅行册永远不上云。** 跨设备、备份、"和 TA 一起编辑同一本册子"——全都做不到，尽管后端代码和测试都写好了。这是一整套死代码，也是一整份被浪费的工时。

**附带一个会当场炸的配置问题**：`.env` 里 `EXPO_PUBLIC_API_ORIGIN=` 是**空的**。`api-client.ts:42-43` 在 origin 为空时退化成相对路径 `/api/health`。真机上 `fetch("/api/health")` 直接抛错 → `network_unavailable`。**现在拿手机跑，gift 页和 /backend 页应该是全线报错的。** `eas.json` 里指向 `https://api.onetapreality.com`——先确认这个域名今天是不是活的。

## 三、必修 bug 清单

### P0-1　多选删除是硬删除，但文案说进回收站

- `src/app/(tabs)/index.tsx:63-70` → 调 `deleteMemory()`
- `src/storage/memory-repository.ts:291` → `DELETE FROM memories WHERE id = ?` **物理删除**
- 而 Alert 文案写的是「会移入回收站，可在回收站里恢复或彻底删除」

用户长按多选删掉 5 本册子，回收站里一本都找不到，数据永久没了。**而且详情页 `memory/[id].tsx:36` 用的是 `discardMemory()`（软删）**——同一个"删除"动作，两条路径行为完全相反。

修：`index.tsx` 里把 `deleteMemory` 换成 `discardMemory`。一行。

### P0-2　「重新生成」两个不同草稿必炸

- `memories-provider.tsx:126` 的 `retryDraft` 直接把 `generator.generate()` 的结果写库
- 它**没走** `memory-factory.ts:21` 的 id 命名空间化（正常路径会把 page id 前缀成 `${memoryId}:cover`）
- 所以 retry 之后写进 `story_pages` 的主键是裸的 `"cover"` / `"photo-1"` / `"closing"`
- `story_pages.id` 是**全局 PRIMARY KEY**（`memory-repository.ts:37`）

→ A 草稿点一次「重新生成」写入 `cover`；B 草稿再点「重新生成」→ UNIQUE 冲突 → 用户只看到「暂时无法重新生成草稿，请重试」，重试一万次都是这个结果。

修：`retryDraft` 里对 pages 补 id 前缀，或直接复用 `createMemoryRecord`。

### P0-3　字体加载失败 = 永久白屏

`src/app/_layout.tsx:17-20`：

```tsx
const [fontsLoaded] = useFonts(appFontSources);
if (!fontsLoaded) return null;
```

`useFonts` 返回的是 `[loaded, error]`，**error 被丢掉了**。字体加载失败 → `fontsLoaded` 永远 false → 永远 `return null` → 一块白屏，无提示、无重试、无日志。现场 Metro 抖一下就是这个后果。

修：`const [loaded, error] = useFonts(...); if (!loaded && !error) return null;`

### P0-4　编辑器 1:1，导出 3:4，所见非所得

- `types/memory.ts:79`：`CanvasLayout.aspectRatio` 恒为 `1`，编辑器按**正方形**摆位，元素坐标是归一化的（0~1）
- `share-action-sheet.ts:81-82`：导出用 `PAGE_WIDTH=360, PAGE_HEIGHT=480`
- `page-capture-provider.tsx:245-251`：把同一份归一化 layout 渲染进 360×480 的容器

→ 一个 `width:0.2, height:0.2` 的方形贴纸，在编辑器里是 72×72，在 PDF 里变成 72×96，**纵向被拉长 33%**。用户精心摆的版，导出后是变形的。

最快的修法：把导出改成正方形（`PAGE_WIDTH = PAGE_HEIGHT = 480`，PDF 纸张 `612×612`）。一致性优先于纸张好看。

### P1-5　多选「分享」静默只导第一本

`(tabs)/index.tsx:41-51`：选了 5 本，`showShareActionSheet` 只吃 `selected[0]`，其余 4 本无声丢弃。用户以为导了 5 本。

修：选中数 > 1 时禁用分享按钮，或提示「当前仅支持单册导出」。

### P1-6　Web 端「日期」是个死按钮

`memory/new.tsx:269-296` 只写了 `Platform.OS === "android"` 和 `=== "ios"` 两个分支。web 上点「日期」这一行**什么都不会发生**。你们 `app.json` 里 `web.output: "server"`，如果 demo 走网页版（很可能，因为真机要 dev build），这就是评委第一个点到的死按钮。

### P1-7　`/activate` 直接暴露开发者控制台

`src/app/activate.tsx:10` → `DeveloperNfcConsole`。这个组件（`features/gifts/developer-nfc-console.tsx`）能列出/创建/激活/退役所有礼品卡，全英文界面，输入框提示是 `"Optional batch, order, or note"`。

而且 `app.json:33-36` 给它配了 `https://onetapreality.com/activate` 的 App Links —— 这是个**公网可达的内部管理后台入口**。

修：加 `__DEV__` 或环境变量门禁。5 分钟。

### P1-8　`.tralbum` 导出是纯噪音

`share-action-sheet.ts:25-28` 给用户两个选项，其中一个是**没有任何软件能打开的自定义 JSON**。同时 PNG 导出被写死成 `Alert.alert("提示", "...当前版本暂不支持逐页 PNG 导出")`（line 331）。

用户想要的是图片，你给了 PDF 和一个不明格式。**小红书赛道的刚需是竖版图片**，这个洞必须堵。

修：删 `.tralbum`，换成「导出图片」。实现成本很低，见第五节。

### P2 杂项

- **照片数量无上限**（`validation.ts` 只校验 ≥1）。选 100 张 → 100 页 → 每页文案一样 → 导出要截 100 次图（每页 ≥100ms 延时 + 3x 渲染 + captureRef）。现场必卡死。**加个 20 张上限**。
- **文档已被代码推翻**：`docs/AI-CONSTRAINTS.md` 说禁云服务，代码里有 R2/Resend/Postgres；`docs/NFC-HANDOFF.md` 说 Expo Go 没 NFC 模块，`package.json` 里插件已装。`AGENTS.md` 引用的 `docs/EXECUTION-CHECKLIST.md` 和 `docs/DECISIONS.md` **根本不存在**。评委不看这些，但你们自己和 AI 协作时会被误导。
- **`gift-entry.tsx` 整个文件用 `\uXXXX` 转义写中文**，单行 3000+ 字符。这个文件现在改不动，今天如果要动 gift 流程，先把它 unescape 成正常中文。
- `expo-file-system/legacy` 是 SDK 54 的弃用导入路径（`share-action-sheet.ts:3`）。
- `_layout.tsx:21` 在 render 期间调用 `configureDefaultTypography()` 做全局 mutation。能跑，但 React 19 + reactCompiler 下是定时炸弹，应移到 useEffect 或模块顶层。

## 四、操作逻辑锐评（不是 bug，是产品判断）

**跳转逻辑：作品诞生的高光时刻被跳过了。**

```
memory/new  --replace-->  memory/review/[id]  --replace-->  "/"（列表页）
```

用户辛苦选完照片、编辑完版式、点「保留草稿」，然后被扔回首页列表，**看不到自己刚做完的成品**。最该发生"哇"的那一秒被换成了一个列表页。改成 `router.replace("/memory/" + id)`，一行代码，情绪价值翻倍。这是今天投入产出比最高的一行改动。

**「生成旅行册草稿」是工程师视角的按钮名。** 用户不知道什么叫草稿，也不关心。叫「生成我们的旅行册」。

**首屏没有"你的东西"。** hero 卡里塞了：标题 + slogan + 两句副标题 + 两个按钮 + 一个文字链，第一屏全是营销文案。杭州示例册应该**以一本书的形态直接出现在首屏**，能翻，翻两页就懂了。现在它是一行小字「先翻一册杭州示例 ›」。

**商店占了 1/4 的黄金 tab 位，卖的是"未来会有"的东西。** 黑客松评委看到底 tab 里有「商店」，第一反应是"这部分是假的吧"。而且首页已经有一个商店入口卡片了。建议：tab 从 4 个减到 3 个，商店降级为入口。省下的那个位置，如果 AI 做出来了，放「AI 重写」入口。

**城市系统是第二个产品。** 城市地图 / 城市档案 / 未打卡城市 / 城市收藏管理 —— 四个层级在讲同一件事（我去过哪些城市）。36 个城市写死在 `types/city.ts`，去了个县城没法记。这套收集玩法的成本已经付了（连 SVG 墨卡托校准都做了），但它和"AI 生成旅行册"的主线关系很弱。今天不要再往这里投一分钟，demo 里给它 20 秒就够。

**生成方式锐评（补一刀）：** 现在的"生成"是「1 张照片 = 1 页」的机械映射。真正值钱的是**编排**——哪几张该并在一页、哪张该做跨页大图、哪张该被丢掉。你已经有 `auto-layout.ts` 和 `MAX_PHOTOS_PER_CANVAS_PAGE` 了，也就是说多图排版的能力在，但生成器根本没用它。**让 AI 决定"分组和取舍"，比让 AI 写几句抒情文案更能打动评委**，而且这才是 40% 那一项想看到的东西。

## 六、赛道适配度（诚实版）

### B站方向一：产品创意 —— 中等偏低，但有救

B站的赛道背景通篇在讲**内容社区、UP主、弹幕、直播、二创**。你做的是**私人**旅行相册。生态几乎不搭 —— 这是要面对的现实。

评分拆开看：
- AI 应用创新性 40% → 现在接近 0，做完下午那 4 小时能到中等
- 实现的可落地性 20% → **你们的强项**（111 测试、真实迁移、真实后端、EAS 配置）
- 产品体验完成度 20% → **你们的强项**（画布编辑器是真的）
- 未来扩展性 20% → 靠叙事，可以打

策略：**别硬掰"我们和B站很搭"，评委一眼看穿。** 换成"这套照片→图文内容的自动编排引擎，本身就是 B站图文/动态投稿的生产力工具"，把扩展性那 20% 讲实。答卷写法见另一份文件。

### 小红书 Build in Public —— 适配度最高，但有硬门槛

旅行 + 照片 + 手账 + 情侣纪念，这就是小红书的核心内容池。产品侧几乎不用改叙事。

**硬门槛**：赛道核心玩法是"在小红书持续发布构建记录"，评选依据明确写了"笔记数据表现与内容质量"。这个骗不了。**今天必须发 3-5 条笔记**，选题我在答卷里给了。晚发一天，社区人气奖（3000 元）基本没戏，但常规奖项还能争。

### 智能少年：做唯一 —— 适配度取决于你们自己，不取决于代码

评分：唯一性 40% + 真实性 40% + 完成度与想象力 20%。

**注意这个结构**：你们最强的那一项（工程完成度）在这里只值 20%。而 40% 的「真实性」明确问"这几天有没有真人用过它、反馈是什么"，40% 的「唯一性」问"为什么是你"。
