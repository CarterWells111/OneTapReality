## 二、新后端的客观评价：这一块是可以拿出去讲的

不是玩具，几处设计比很多生产项目严：

- **邮箱验证码登录**：account + session 分离，15 分钟窗口内重复请求限流（`api/auth/request+api.ts:24`）
- **礼品权限模型**：一个 owner + 最多 3 个访问邮箱，viewer 只读，`requireOwnedGift` 统一守门
- **发布是两段式提交**：POST 建 publication session + 10 分钟有效的预签名 PUT URL → 客户端逐张直传 R2 → PUT 提交前用 `HeadObject` **逐张校验 contentType 与 byteSize 完全一致**，全部通过才落库（`my-gifts/[id]/publish+api.ts:49-53`）。上传中断不会产生半个相册。
- **边界都设了**：100 页 / 50 张 / 单张 25MB / publication 15 分钟过期
- **停用礼品 + 后台媒体清理**（`api/internal/gift-maintenance`）
- **开放重定向防护**：`login.tsx:8-11` 的 `safeReturnTo` 挡了 `//evil.com`

评委问"你们后端做了什么"，讲这段：**两段式发布 + 提交前对象校验**。这是能证明工程能力的具体细节。

## 三、新增的 P0

### N-1　整套新后端在当前 `.env` 下一行都跑不起来

`.env` 里只有三个变量：`DATABASE_URL` / `DEVICE_TOKEN_PEPPER` / `PORT`。
而 `.env.example` 要求 11 个。缺的每一个都打死一条链路：

| 缺什么 | 后果 |
|---|---|
| `GIFT_AUTH_PEPPER` `RESEND_API_KEY` `GIFT_EMAIL_FROM` | `/api/auth/request` 直接 500 `server_configuration_missing` → **登录不可用** → 我的纪念品 / 认领 / 发布 / 管理**全线不可用** |
| `R2_ACCOUNT_ID` `R2_BUCKET` `R2_ACCESS_KEY_ID` `R2_SECRET_ACCESS_KEY` | `/api/my-gifts/[id]/publish` 503 `gift_media_unavailable` → **发布共享相册不可用** |
| `GIFT_TOKEN_PEPPER` | `/api/gifts/[token]/entry` 起不来 |
| `GIFT_ADMIN_EMAILS` | 管理端 API 全部拒绝 |

**唯一配好的那个 `DEVICE_TOKEN_PEPPER`，服务的是全项目没人调用的死链路。**

如果 Railway 上都配齐了，那就是"本地跑不通、线上能跑"。**今天必须在真机上实测一次线上**，不要明天第一次试。

**顺带一个更要紧的问题**：`npm run verify:backend` 这个 smoke test 只覆盖 `/api/health` → `/api/devices/register` → `/api/memories` CRUD —— **全是死链路**。它绿了不代表登录能用、礼品能发。你们的自动化验收测的是唯一不用的那条路。今天补一个覆盖 auth + gift 的手动 checklist 就够，不用写代码。

### N-2　收礼人看到的不是你排的册子，是一列裸照片

`gift-entry.tsx:33-34`：

```ts
const album = await client.getGiftAlbum(token, accessToken);
setPhotos(album.media.map((media) => media.readUrl));
```

然后 `photos.map(uri => <Image height={240} width="100%" />)`。

发布时 `gifts/[id].tsx:20-23` 的 `sharedPage()` 剥掉了 `photoUri` 和 `coverImage`，pages（含完整 layout）照样上传存进 Postgres —— **但接收端根本不渲染 layout**。

结果：你花了整个画布编辑器的力气排的版、贴的贴纸、调的封面色、写的文字，收礼人**一个都看不到**，只看到 240pt 高的照片一张张往下滚。

**"我给你做了一册"是整个产品的核心情感价值，它在接收端目前是 0。** 如果明天要讲送礼这条线，这是最该补的一处。

### N-3　layout 里的本地 `file://` 路径被原样上传了

`sharedPage()` 只删了顶层两个字段。`page.layout.elements[].uri`（图片元素）和 `page.layout.coverImage` **原样保留**——里面是发送方手机的 `file:///var/mobile/.../ImagePicker/xxx.jpeg`。

两个后果：
1. 一堆毫无意义的本机绝对路径进了服务端数据库，属于不必要的数据外泄（而且 `docs/AI-CONSTRAINTS.md` 里你们自己写过"照片不离开设备"这条原则）
2. 将来接收端要渲染 layout，这些 uri 全是死链

修法与 N-2 是同一件事：`sharedPage()` 把 layout 也过一遍，image 元素的 `uri` 换成 `mediaSlot: number`，接收端拿 `readUrl` 按 slot 回填，再用现成的 `PageReader` 渲染。

### N-4　`media.position` 和 `pages.position` 是两套坐标系

- `gifts/[id].tsx:57`：media 的 position 来自 **photoPages**（只含有照片的页）的下标
- `gifts/[id].tsx:65`：pages 的 position 来自 **完整 pages** 的下标

封面没有 `photoUri`，所以 `media[0]` 实际对应 `pages[1]`。服务端和接收端都拿不到这个偏移关系。

**照片和页面的对应关系在"发布"那一刻就永久丢失了。** 这是 N-2 不能简单修好的根因——必须先把 slot 映射建立起来。

### N-5　HEIC 会在接收端裂图

`gifts/[id].tsx:12-18` 的 `imageContentType()` 按**文件扩展名**判断，`.heic` 会以 `image/heic` 预签名并上传。

iOS 相册里大量照片是 HEIC。**Android 和浏览器不显示 HEIC。** 而提交前的 `HeadObject` 校验只比对 contentType 是否一致，不会拦住这个问题——它会"发布成功"，然后在对方手机上全裂。

修法：`launchImageLibraryAsync` 之后统一转 JPEG（或上传前压缩转码）。顺带能把上传体积降一个数量级，20 张照片的发布时间从几分钟降到几十秒。

**另外**：发布多张照片时只有一个 `busy` 布尔，没有进度反馈。会场 wifi 下用户会以为卡死。加一行「正在上传 3/12」。

## 六、关于「AI 不接入，只走故事」

这个决定我理解（审核风险、时间、合规）。但有一件事要提醒：**B站方向一评分表第一项就是「AI 应用创新性 40%」**。

如果答卷写"AI 生成"、现场说"AI 帮你生成"，评委问一句"用的什么模型 / 现在是真的在调吗"，答不上来的代价**比丢掉这 40% 更大**——它会连带污染"落地性"和"完成度"的印象分。评委见过太多把模板包装成 AI 的项目，被抓到一次，整份答卷的可信度都要打折。

### 建议口径（对内诚实、对外站得住）

1. 不说「AI 生成」，说**「自动编排」**
2. 主动把 AI 讲成**已经预留好的接口，并且能指着代码讲**：
   - `createRemoteDraftGenerator(transport, consent)`（`remote-contract.ts:150`）是标准依赖注入点
   - `RemoteDraftRequest`（`:26-33`）在**类型层面**就限定了只传元数据、不传照片
   - `findPrivacyViolations()`（`:96`）是发送前的最后一道正则防线
3. 被追问就正面答：

> 目前是确定性编排 + 全量可编辑。模型接入点已经就绪，一个 transport 的事。没上线是因为我们不想在还没有内容审核方案的时候，把用户的私人旅行照片交给第三方模型——这条边界我们从第一行代码就写进类型定义里了。

**这个回答会加分，因为它显示你想过合规**，而合规恰好是"可落地性 20%"想看的东西。你们真的有这个抽象，所以这不是话术，是事实。

## 七、关于「亲友已体验」（智能少年赛道）

原题是「谁是它的真实用户？**这几天有没有真人用过它？**反馈是什么？」

亲友反馈**可以用，但必须标明是亲友**，理由：

- 评分表「真实性 40%」，赛道原文是"敢不敢给真实用户用、有没有人真的需要"
- 亲友反馈天然偏正面，评委看多了能分辨
- 反过来：**诚实标注 +1 条陌生人反馈 +1 条负面反馈**的组合，比五条匿名的"用户说很好用"可信十倍

**今天的成本收益**：抓 3 个陌生人，20 分钟，拿 3 句原话。**这是今天投入产出比最高的一件事**——它直接命中 40% 的评分项，而修 bug 只影响"完成度与想象力"那 20%。脚本在 `赛道答卷草稿.md` 附一。
